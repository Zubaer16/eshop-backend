## Scope implemented in this single incremental Backend overlay

1. **Credential abuse resistance**: narrowly scoped PostgreSQL fixed-window limiter before the auth controllers, DB-clock windowing and atomic upsert across VPS/Vercel instances, exact POST route policy only, `429` with `Retry-After`, generic `503` fail-closed on DB errors. No account-enumeration response, no raw IP/headers, email, session or token in the new table. `key_hash` is HMAC-SHA256 keyed by the installation's existing JWT secret, separate domain string; rotating that secret naturally clears the active throttle key-space. **Not** a substitute for WAF, per-account anomaly detection, DDoS edge controls or CAPTCHA. No external provider/webhook/financial routes are intercepted.
2. **Proxy IP safety**: `TRUSTED_PROXY_CIDRS` accepts an explicit <=16 entries of exact IPs or limited CIDRs; defaults to direct socket IP, never trusts client X-Forwarded-For automatically. Operator must establish actual trusted ingress ranges. Never set `trust proxy=true` or `0.0.0.0/0`. Without correct proxy configuration, shared egress/NAT users may share a bucket; test this with a staging edge.
3. **Default & compatibility**: `AUTH_ABUSE_LIMIT_ENABLED` defaults `false` for development/test, `true` for production, and cannot be disabled in production. **G11 migration must be applied before starting production code** or protected credential operations fail closed. Auth REST success payloads and existing authorization/session semantics are unchanged. Swagger adds 429/503 metadata on auth controllers.
4. **Privacy**: HTTP logs now record matched Express route templates rather than real UUID/path/query values; unmatched routes log `/unmatched`; no change to audit, financial or outbox retention. Existing helmet/CORS run before throttling so rejection responses get their headers.
5. **Operations**: read-only schema/migration checksum-and-identity audit, offline redacted release preflight, read-only HTTPS deployment smoke, manual preview/opt-in bounded auth-bucket retention, verified `pg_dump`/SHA256/`pg_restore --list` backup and **scratch-only** restore rehearsal PowerShell helper, Docker VPS candidate, and vendor-specific acceptance checklist. Provider credentials remain environment-owned; none are distributed.
6. **Tests authored but NOT run**: route/key/failure unit tests, config rejection tests and 20-parallel-request real-PostgreSQL API DB test. This follows the owner decision to defer G5–G11 automated suites until G12, without weakening assertions.

## DB migration and retention

New **additive** `20261105130000_phase05j_g11_auth_abuse_limit` creates only `auth_abuse_buckets` with a hashed key, UTC window-start timestamp, bounded attempt counter, expiry and index. No previous migration SQL, users, auth sessions, payments, orders, scheduler lane or provider tables are changed. Source now has **40 migration directories** (39 pre-existing including G10); that is NOT 40 applied DB migrations. Run the checksum/identity audit against **each** owner DB separately before backup, and after the additive migration.

`node -r dotenv/config scripts/g11-prune-auth-buckets.cjs --expect-db=<database>` is read-only preview; `--apply` deletes at most 1,000 expired rows from one verified database after an extra 24-hour grace. It does **not** prune audit/outbox/provider evidence. No default cron lane added to G10: manual or owner-reviewed scheduling only.

## Deployment sequence / rollback boundaries

1. Identify actual live working-tree state, review `git status`, install guarded overlay only if manifest hashes match. Do **not** overwrite divergent files.
2. Validate dev/test DB names, applied migration checksums, no unresolved failures; take **separate fresh verified backups** and test archive listing, ideally a separate offline restore rehearsal. Review migration SQL; `prisma migrate deploy` on each intended DB only.
3. Perform static checks and record log evidence. Keep provider sends and G10 scheduler disabled while static/DB correctness is reviewed.
4. On staging, set HTTPS origins, strong per-installation secrets, explicit trusted proxy IP/CIDR if applicable, independent runtime/migration URLs; run redacted preflight, health/unauthenticated-admin/docs smoke, provider control-case verification under manual oversight.
5. Additive rollback means **revert application release to the prior version** while leaving the new unused security table in place. No `migrate reset`, `db push`, editing historical SQL or destructive down-migration. For real failure, diagnose and apply a separately reviewed forward fix. Database restore is a deliberate incident recovery, never an automatic rollback.
